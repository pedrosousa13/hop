# The latency gate — p95 under 10 ms plus the adversarial arm (Issue #61, closes #30, #46) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended) or superpowers:executing-plans, plus superpowers:test-driven-development. Work task-by-task, red-green-refactor, and keep the workspace green at every task boundary.

**Goal:** Land the two-arm latency gate spec §11's 2026-07-31 amendment describes — a scripted 10 000-item fixture asserting p95 query latency under 10 ms, and a second, adversarial arm asserting a *bounded worst case* over pathological input — and, as the acceptance criteria demand, actually discharge #30 (provider output unbounded at assembly) and #46 (query term unbounded before pattern construction) rather than merely working around them in the test fixture. Both arms run in CI on every pull request, not only on `main`.

**Why this is one slice and not three:** §11 says explicitly the adversarial arm "forces #46's input cap to be decided in M2 rather than discovered in production" — the gate cannot pass without the caps existing, and the caps have no reason to exist without the gate proving they work. #61's brief and both #30/#46's Agent Briefs are folded into one worked plan.

## Architecture today

- **The trust boundary #30 names is real and unguarded.** `CheckedItems::check` (`pipeline.rs:429`) is the *only* constructor of the *only* item collection `Pipeline::assemble` accepts — the module's own docs call this "the enforcement" — but today it checks only `kind` and `provider` against the producing manifest. It does nothing about item **count** (a provider can hand it a `Vec<Item>` of any size) or **field length** (`title`, `subtitle`, `copy_text`, an item's `actions` — all plain `String`/`Vec` fields with no constructor-level bound, unlike `ItemId`/`ActionId`, which already refuse an over-long value at `ItemId::new`/`ActionId::new` regardless of where they're built). `Pipeline::assemble`'s only cap is `ranked_items.truncate(max_results)` at the very end (`pipeline.rs:809`) — it runs after boosting, after the pin-budget split, after ranking's own haystack allocation and title-cloning dedupe key.
- **`ProviderHost::run_one`** (`host.rs:665-752`) already calls `CheckedItems::check(vec![output])` once per single provider's answer to one query, before that answer is sent anywhere — this is the exact seam where a per-provider-answer bound composes for free with existing code; nothing about `run_one`'s call site needs to change.
- **The term has no ceiling.** `Ranker::rank` (`rank.rs:269`) calls `Matching::for_term(query.term.trim())`, which builds a `nucleo_matcher::Pattern` directly from whatever length the term is (`rank.rs:414`, `Pattern::new(term, ...)`). `ProviderManifest::min_term_len` (`provider.rs:84`) is a *minimum* — a per-provider pre-filter deciding whether to run the provider at all — not a length applied inside the ranker, and nothing plays the maximum's role.
- **`hop_protocol::limits`** is the house precedent for how a cap constant is named, documented and justified (one constant per field, byte-denominated, a worked "what these bounds compose to" table, a test that recomputes the table from the constants). Its own docs already name the gap this plan closes, in two places: the `MAX_ITEMS_PER_QUERY` doc says the field-length obligation on in-process-built items is "documented, not enforced — wherever an item is built in-process"; `hopd::source::ResultSource`'s trait doc says "neither `ProviderHost` nor this source caps how many items one provider may answer with... Closing that is issue #30's."
- **`hopd`'s own caps are a different layer and stay unchanged.** `MAX_ITEMS_PER_QUERY` (hop-protocol, 5 000) bounds what the daemon's *accumulator* holds across every provider arrival for one query (`source.rs`'s `start`); `MAX_ITEMS_PER_RESULTS_FRAME` (1 000) bounds one wire frame. Both already exist and are out of this slice's scope — this plan adds a *third*, narrower cap, inside `hop-core`, at the point one provider's *single* answer enters assembly, which is what #30 actually asks for ("bounded... before boosting and ranking rather than after").
- **No benchmarking dependency exists**, and `deny.toml`'s GPL-3.0 license allow-list plus its "reviewed, not grandfathered" posture means any addition needs the same prose-justification the `toml` entry got in #60's plan.

## Global Constraints

- **Four gate commands, all required at every task boundary:** `cargo test --workspace` · `cargo fmt --all --check` · `cargo clippy --workspace --all-targets -- -D warnings` · `cargo deny check`.
- **No `.unwrap()` in production code** (`clippy::unwrap_used` + `-D warnings`). Test files / test modules open with `#![allow(clippy::unwrap_used)]`.
- **Zero new dependencies.** See Decision 5 below — plain `#[test]` + `std::time::Instant` in `--release` is the whole mechanism.
- **`std::env::set_var` is unavailable** (workspace denies `unsafe_code`); nothing in this slice needs it — no test here spawns the real `hopd` binary or reads env.
- **No AI attribution** in commits or the PR.
- **Reuse `hop_protocol::limits`'s existing constants rather than inventing parallel ones** wherever a field bound already exists there (title, subtitle, copy_text, action label, action count) — see Decision 1's coherence table.
- **`cargo test --workspace` must stay debug-mode-fast and stay green without `--release`.** Both new timing tests are `#[ignore]`d for that reason; only the new CI job runs them, in `--release`.

## In scope — the issue's acceptance criteria (folding in #30 and #46)

1. A scripted 10 000-item index fixture exists and is deterministic.
2. CI asserts p95 query latency under 10 ms over that fixture.
3. CI asserts a bounded worst case over pathological input: long query, oversized candidate set, huge per-item strings.
4. A maximum term length is decided, documented beside the existing minimum, and enforced before pattern construction (#46).
5. Provider output is bounded in count and per-field length where it enters assembly, before boosting and ranking rather than after (#30).
6. Ordinary queries rank identically to before this slice.
7. Both arms run on pull requests, not only on the default branch.

Explicitly **out of scope**: changing the ranking algorithm or dedupe rule; a config knob for any of the new caps (they are hard safety ceilings, like `MAX_PINNED_ITEMS_PER_PROVIDER`/`_QUERY`, not tuning parameters); bounding a provider's own `query()` implementation's cost before it returns (a hostile provider can still spend its own CPU/memory building an oversized `Vec<Item>` — this slice bounds what assembly does with what it receives, matching #30's own framing); wire-level query length (already `MAX_QUERY_TEXT`, unchanged); item identity validation (#31, separate).

## Design decisions

### 1. The cap values

| Cap | Value | Enforced in | Truncate or reject | Why |
| --- | --- | --- | --- | --- |
| Maximum term length | **256 chars** | `hop-core/src/rank.rs`, `Matching::for_term` | **Truncate** (keep the first 256 chars) | A typed launcher query is a few words; 256 chars is generous for a legitimate long paste (a sentence, a full path) while keeping worst-case pattern-construction cost tiny. It sits well under `hop_protocol::limits::MAX_QUERY_TEXT` (1 024 bytes, the wire's whole-query cap) — coherent, not competing: `MAX_QUERY_TEXT` bounds what a client can send at all; `MAX_TERM_CHARS` bounds what actually reaches `Pattern::new`, and it is the *only* cap on the alias-rewrite sink, which is **not** wire-bound at all (`Pipeline::assemble` substitutes an alias's rewrite target — arbitrary text from a config file — as the effective term; see `rank.rs`'s own module docs on why escaping/bounding has to happen at this one seam). Truncating rather than rejecting matches the UX cost of the two failure modes: rejecting an over-length query wholesale would blank the result list on a legitimate long paste; truncating still returns a plausible (if degraded) match. This differs from the wire's own "refuse rather than shorten" identity-field philosophy (`limits.rs`'s own docs: "silently shortening an id would produce a different id") deliberately — a search term is not an identity, truncating it does not corrupt anything the way truncating an `ItemId` would. |
| Maximum items accepted from one provider's single answer | **1 000 items** (`MAX_ITEMS_PER_PROVIDER_ANSWER`) | `hop-core/src/pipeline.rs`, `CheckedItems::check` | **Truncate** (drop the tail, silently — same "truncate-and-terminate, nothing on the wire naming it" precedent `hopd/src/source.rs`'s accumulator already uses for its own count cap) | Deliberately reuses `hop_protocol::limits::MAX_ITEMS_PER_RESULTS_FRAME`'s value (1 000) rather than inventing a new number: no single provider should be able to hand assembly more raw material than a client could ever legitimately be shown in one wire frame. Every provider that exists today (the skeleton, apps) answers with a handful to a few hundred items; 1 000 is generous headroom, revisitable if a future bulk provider (files, M5) needs its own pagination story — that provider would do its own pre-filtering rather than dumping an entire index into one `query()` answer, consistent with the design spec's "no full index scan on keystroke" latency contract. |
| Per-item field lengths: `title`, `subtitle`, `copy_text`; per-action `label`; action count | **Reuse `hop_protocol::limits`'s existing constants exactly**: `MAX_TITLE` (1 024 B), `MAX_SUBTITLE` (1 024 B), `MAX_COPY_TEXT` (65 536 B), `MAX_ACTION_LABEL` (128 B), `MAX_ACTIONS_PER_ITEM` (32) | `hop-core/src/pipeline.rs`, `CheckedItems::check` | **Reject the whole item** (new `FailedCheck::FieldTooLong { field: &'static str }`, recorded as an ordinary `Rejection` — the existing mechanism) | No new numbers: the wire already prices these exact fields when an item arrives by socket (`limits.rs`'s "What the bounds compose to" table); an item built in-process and never bounded is exactly the coherence gap `limits.rs`'s own docs flag ("documented, not enforced — wherever an item is built in-process"). Reject, not truncate, for the same reason the wire itself rejects rather than shortens these fields — `title`/`subtitle` feed straight into `Ranker::rank`'s haystack and dedupe key, so a truncated-in-place title would silently change what a user sees matched against what they typed, which the wire's own "nothing here truncates to fit" posture already treats as the wrong trade for these fields. Reusing `Rejection`/`FailedCheck` costs nothing new: it is already the mechanism `CheckedItems::check` uses for the two existing manifest checks, and it is already surfaced through `ProviderHost`'s `ProviderLog` (`ProviderEvent::Rejected`) — "the excess is recorded" for free. |

**`id` and `provider` need no new cap.** `ItemId::new`/`ActionId::new` already refuse an over-length value at construction, unconditionally — not just on the wire-deserialize path (`hop-protocol/src/item.rs`: the `Deserialize` impl calls the same `ItemId::new` a hand-built item must also go through). `provider` needs nothing beyond what `CheckedItems::check` already does: the existing provenance check (`item.provider != output.manifest.id`) already rejects any item whose `provider` string doesn't exactly equal the producing provider's `id`, which is a short `&'static str` authored in this codebase — an oversized `provider` string simply fails that check today and is already rejected.

**Where the count cap's cost is *not* bounded, stated plainly:** truncating `output.items` to 1 000 inside `check()` bounds what *assembly* does with a provider's answer. It does nothing about the cost a hostile provider's own `query()` paid to build a larger `Vec<Item>` before returning it — that cost is already bounded elsewhere (`ProviderHost::run_one`'s existing budget/timeout enforcement), and is out of this slice's scope, matching #30's own framing ("provider output is bounded... *where it enters assembly*").

### 2. Where the bound is enforced

- **Term length:** `hop-core/src/rank.rs`, inside `Matching::for_term(term: &str)` (`rank.rs:410`), *before* the `Pattern::new(...)` call at `rank.rs:414` — this is the literal, only call site in the crate that constructs a `Pattern`, so "before pattern construction" names this function precisely. Truncate via `term.chars().take(MAX_TERM_CHARS).collect()` (char-boundary-safe by construction, unlike a byte-index slice) before the pattern is built, and use the *truncated* length for score normalization (`term_chars`), so a truncated term's score isn't diluted by counting characters that were never matched against.
- **Item count + field length:** `hop-core/src/pipeline.rs`, inside `CheckedItems::check` (`pipeline.rs:429`) — the type's own docs call this "the only item collection `Pipeline::assemble` accepts" and "the enforcement" for the two existing manifest checks; extending the same function is the natural, minimal-surface fix, not a new pre-step. Concretely: truncate `output.items` to `MAX_ITEMS_PER_PROVIDER_ANSWER` *before* the existing per-item loop begins (so the loop, and every `Rejection` it might build, is itself bounded to at most 1 000 iterations regardless of what a provider claims to send); then, inside the loop, after the existing kind/provenance checks and before pushing a surviving item into `items`, check `title`/`subtitle`/`copy_text` lengths and the `actions` vector's shape, rejecting on the first failure (matching the existing "reported once, against the earliest-checked failure" precedent the module's `DECISION` comment already states for the two existing checks).
- **Why these are the trust boundaries, and not `Ranker::rank`/`Pipeline::assemble` themselves:** `Ranker::rank` and `Pipeline::assemble` are both documented as *pure* — no allocation-shape decisions belong scattered through their body when one upstream constructor can make the invariant true by construction, the same argument `CheckedItems`'s own docs already make for the two manifest checks ("unchecked items cannot travel the assembly path... The compiler enforces it instead of a reviewer noticing"). `Ranker::rank` stays reachable directly with a bare `Vec<Item>` (as documented today — nothing in this slice closes that residual hole; a caller that bypasses `CheckedItems` still gets an unbounded item count) but gets the term-length truncation unconditionally, since every caller of `rank` — including a hypothetical future bypass — benefits from bounded pattern-construction cost regardless of how the items arrived.

### 3. "Ordinary queries rank identically" — how it's proven

No characterization test is needed beyond what already exists, for one structural reason: every existing pinned-ordering test in `rank.rs`'s and `pipeline.rs`'s `#[cfg(test)] mod tests` — `typo_tolerant_match`, `duplicate_apps_deduped_by_title`, `boost_overrides_fuzzy_order`, `source_weight_breaks_ties`, `dispersed_matches_are_rejected_below_the_real_match`, `provider_scoped_boost_only_applies_to_the_matching_producer`, `empty_term_returns_all_sorted_by_weight_and_boost`, and, in `pipeline.rs`, `inferred_utility_pins_on_top_without_hiding_others`, `alias_rewrite_changes_ranking_term`, `learning_boost_applied_and_beaten_by_alias`, `empty_term_returns_everything_ordered_by_weight_and_boost_with_tail_last`, `max_results_cap_counts_pinned_tail`, and the whole pin-budget suite — every one of them uses terms and item counts far below both new caps (256 chars, 1 000 items/provider). If Task 1/2's truncation guards are written correctly (only firing strictly above the threshold), these tests exercise the *exact same code path* with the new guard as a structural no-op, and running unmodified is itself the proof: `cargo test --workspace` staying green with zero edits to any of these assertions **is** the "ranks identically" evidence, the same way #60's plan relied on existing tests continuing to pass rather than writing a parallel characterization suite. What Task 1 and Task 2 each add on top, deliberately, is a boundary pair per cap — exactly-at-the-cap passes through byte-for-byte/item-for-item unchanged, one-over-the-cap is the first input that changes behavior — mirroring `hop_protocol::limits`'s own `assert_string_boundary`/`assert_count_boundary` pattern, so the "no effect below the line" claim is pinned by a test rather than left to inspection.

### 4. How the p95 arm avoids being flaky in CI

This is the biggest risk in the slice, and the plan makes a firm choice rather than leaving it open.

**The four-gate `cargo test --workspace` command runs in debug mode**, and debug-mode Rust can be 10–50× slower than release for CPU-bound work like fuzzy matching — a 10 000-item p95 assertion of "under 10 ms" run under `cargo test --workspace` as currently gated would be measuring the wrong build and would very plausibly fail or flake on ordinary, unregressed code for that reason alone, independent of CI noise. So:

1. **Both timing tests are `#[test] #[ignore]`** inside a new `crates/hop-core/tests/latency.rs`. `cargo test --workspace` (the fast, always-required gate) never runs them — they cost it nothing and cannot flake it.
2. **A new CI job, `latency-gate`, is added to `.github/workflows/ci.yml` alongside `ci` and `supply-chain`** — its own red/green check, matching the existing `supply-chain` job's precedent for "a different kind of failure deserves a different status." It runs `cargo test --release -p hop-core --test latency -- --ignored --test-threads=1`. `--release` is the load-bearing flag: back-of-envelope from the M1 sweep's own measured rate (≈8.2 ns per term-char × item unit, linear and reproduced three ways in #46's table) at 10 000 items and a realistic ~10-char query is ≈0.8 ms — over 12× headroom under the 10 ms budget in release mode, which is the confidence the gate rests on. `--test-threads=1` keeps the two tests in this one small binary from contending with each other for CPU during measurement, which parallel test execution would otherwise do by default.
3. **This job is declared in the same workflow file whose top-level `on:` already covers `push: [main]` and `pull_request:`** with no branch filter — so simply adding the job satisfies "both arms run on pull requests, not only on the default branch" without any trigger changes.
4. **Warm-up before measurement.** The p95 test runs the fixture query 50 untimed times first (branch predictor, allocator, CPU frequency scaling), then times 500 timed calls, sorts, and asserts the 95th-percentile latency (nearest-rank: index `⌈0.95 × 500⌉ - 1`) is under 10 ms. The fixture (10 000 items, built once outside the timed loop) is varied across a small fixed set of realistic query strings across the 500 calls, not one repeated string, so the measurement isn't gamed by favorable cache/branch-prediction reuse a single fixed query would enjoy.

**Arm 2 (adversarial) is deliberately *not* a percentile, and — the firm recommendation — is primarily a structural, non-wall-clock assertion, with exactly one generous wall-clock backstop, not a tight one.** §11's own amendment text already frames it this way ("a bounded worst case ... rather than a percentile"), and once Task 1/2's caps exist, the interesting property to prove is no longer "how fast is the pathological case" (a fragile, noise-sensitive number) but "**does the cap actually apply**" (a deterministic, zero-flake structural fact). Concretely, arm 2 is three tests:

- **`oversized_provider_input_is_truncated_before_ranking`** (not `#[ignore]`d — fast, deterministic, runs in the ordinary `cargo test --workspace` gate too): feeds `CheckedItems::check` a single `ProviderOutput` with far more than 1 000 items and asserts the surviving count is exactly `MAX_ITEMS_PER_PROVIDER_ANSWER`. No timing involved.
- **`overlong_term_is_truncated_before_pattern_construction`** (same, not ignored): a black-box proof that doesn't need `Matching` to be `pub`. The term is `"a".repeat(MAX_TERM_CHARS + 1000)` (a pathological, non-bailing-out repeated character, over the cap); the one candidate item's haystack is `"a".repeat(MAX_TERM_CHARS)` exactly. nucleo's subsequence matcher requires every needle character to align in order: an *un*truncated term needs `MAX_TERM_CHARS + 1000` matching characters from a haystack of only `MAX_TERM_CHARS`, which has no valid alignment (`None`, item dropped); a term truncated to exactly `MAX_TERM_CHARS` matches the equal-length haystack trivially (item found). Asserting the item **is** found is therefore a deterministic, timing-free proof that truncation ran before `Pattern::new`.
- **`bounded_worst_case_completes_promptly_in_release_mode`** (`#[ignore]`d, release-only, same CI job as arm 1): the one wall-clock check, and the one place a *regression* in the caps' own effectiveness (not their mere presence) would be caught — e.g. a future change that raises a cap without reconsidering the cost, or reintroduces quadratic work elsewhere within the capped bounds. Builds the true worst case *within* both caps: 10 provider-outputs of 1 000 items each (right at `MAX_ITEMS_PER_PROVIDER_ANSWER`, so nothing is truncated away — this is deliberately the maximal *legal* input, not an over-cap one), every item's `title` at exactly `MAX_TITLE` bytes of a repeated non-bailing-out character, queried with a term at exactly `MAX_TERM_CHARS` of the same pathological character. Asserts the whole `Pipeline::assemble` call completes in **under 1 second** — a deliberately generous ceiling (the same back-of-envelope arithmetic as arm 1 puts the expected cost at tens of milliseconds, so this is ~20–50× headroom, chosen specifically to make this test durable against CI jitter while still catching a real algorithmic regression, which would blow past 1 second by a wide margin rather than by a hair).

### 5. Whether a benchmarking dependency is warranted

**No. Zero new dependencies.** `criterion` (the obvious candidate) is built for statistical regression-tracking across historical runs via `cargo bench`, reported outside the normal test harness — it has no native "fail the build against a fixed threshold" mode, which is exactly what this gate needs (a fixed 10 ms / 1 s ceiling, not a comparison against a stored baseline). Adopting it would mean a new dependency to justify in `deny.toml`'s reviewed prose (matching `toml`'s precedent in #60's plan) for a feature this slice doesn't use, plus a second, `cargo bench`-shaped CI invocation alongside the `cargo test --release -- --ignored` one this plan already needs. Plain `#[test]` + `std::time::Instant`, run in `--release` with warm-up and a generous margin, gets the same guarantee with the same tool every other test in this workspace already uses.
